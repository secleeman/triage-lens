# Phase 2 要件 — 入力形式と出力言語を広げる

## ゴール
Phase 1 で作った「Trivy JSON → 日本語トリアージレポート」を、次の2方向に広げる。

- **入力**: CycloneDX 形式（JSON）の SBOM も読める
- **出力**: 英語のレポートも出せる

```
triage-lens report sbom.cdx.json -o triage-report.md
triage-lens report trivy-result.json --lang en -o triage-report-en.md
```

Phase 1 の既定動作（Trivy JSON 入力 / 日本語レポート）は一切変えない。

## スコープ
1. CycloneDX 形式（JSON）の SBOM 入力対応
2. 英語レポート対応（`--lang en`。既定は日本語のまま）
3. README 更新（新機能の使い方、日英）

上記以外は実装しない。

## 機能要件

### 1. CycloneDX（JSON）入力

#### 対象とする入力
- CycloneDX の **JSON** 表現。仕様バージョンは 1.4 / 1.5 / 1.6 を想定する
  （脆弱性情報 `vulnerabilities` が仕様に入ったのが 1.4 のため）
- XML 表現は対象外
- 脆弱性の一覧（`vulnerabilities` 配列）を持つ BOM を対象とする。
  `components` しか持たない純粋な部品表は、脆弱性0件として扱う
  （triage-lens 自身は脆弱性を検出しない。あくまでスキャナ出力の優先順位付けが役割）

#### 形式の判別
- 入力ファイルの形式は **自動判別** する。利用者は形式を指定しなくてよい
  - `bomFormat` が `"CycloneDX"` → CycloneDX として読む
    （仕様上の値はこの文字列ちょうどなので**厳密に一致**させる。大文字小文字や
    前後の空白を許すと、`Results` を持つ Trivy 出力が CycloneDX と誤判定され、
    検出結果が黙って0件になってしまう）
  - `Results` キーを持つ → Trivy JSON として読む
  - どちらでもない → 入力エラー（終了コード2）。エラー文には
    両方の形式に対応していることと、生成コマンド例を示す
- 判別は「先に CycloneDX、次に Trivy」の順で行う。両方の特徴を持つ入力は
  実運用では存在しないが、順序を決めておくことで挙動を一意にする

#### フィールドの対応
| triage-lens の項目 | CycloneDX の取得元 | 取得できない場合 |
| --- | --- | --- |
| 対象名 | `metadata.component.name`（あれば `@version` を付ける）→ 無ければ `metadata.component.purl` | `(名称不明)` |
| CVE ID | `vulnerabilities[].id` | その脆弱性は読み飛ばす |
| パッケージ名 | `affects[].ref` から `components[].bom-ref` を引いて `name`。`metadata.component` の `bom-ref` も引き当ての対象に含める | `(不明)` |
| 現バージョン | 引き当てた component の `version` → 無ければ `affects[].versions[]` の `status: affected` のエントリ | `(不明)` |
| 修正バージョン | `affects[].versions[]` の `status: unaffected` のエントリ（`version` または `range`）が**ちょうど1件**のときだけ採用する | 「不明」（後述） |
| 検出箇所 | 引き当てた component の `purl` → 無ければ `bom-ref` → 無ければ対象名 | `(検出箇所不明)` |
| CVSS | `ratings[]` の `score`。`method` が現行世代（`CVSSv3` / `CVSSv31` / `CVSSv4`）のものを優先し、無ければ `CVSSv2`。同じ世代に複数あれば `source.name` に `nvd` を含むものを優先し、それも無ければ最大値 | 不明（`None`） |

- 1つの脆弱性が複数の component に影響する場合（`affects` が複数）、
  **component ごとに1行**として展開する。Phase 1 と同じ「検出箇所が違えば別の行」の方針に合わせる
- `affects` が空、または参照先の component が見つからない場合も、
  CVE ID が読めていれば1行として残す（パッケージ名は `(不明)`）
- 重複除去は Phase 1 と同じキー（検出箇所 / CVE ID / パッケージ名 / 現バージョン）で行う
- `components` は入れ子にできる仕様のため、たどれる範囲をすべて索引に含める
  （壊れた入力で再帰が止まらなくならないよう深さの上限を設ける）
- `method` が書かれていない `ratings` や、CVSS 以外の尺度（`other` / `OWASP` / `SSVC`）の
  スコアは **CVSS として扱わない**。尺度の違う数値を CVSS 欄に出すと誤解を招くため、
  「不明」と表示する側に倒す
- 世代の違うスコア（v2 と v3系）を混ぜて最大値を取らない。実態より高い深刻度になるため

#### 「修正版なし」と「修正版が不明」を区別する
CycloneDX には「修正版が存在しない」ことを明示する項目がない。
`status: unaffected` のエントリが無い場合、それは

- 修正版が本当に存在しない
- 生成ツールが修正版を書き出していない

のどちらとも判断できない。**取得できていない値を断定しない**という Phase 1 からの
方針に従い、この場合はレポートに「修正版なし」ではなく **「不明」** と表示する。

さらに、`unaffected` は「その版は影響を受けない」という意味でしかなく、
**修正版とは限らない**（脆弱性が入る前の古い版も `unaffected` になりうる）。
`unaffected` のエントリが複数ある場合はどれが修正版か決められないため、
やはり「不明」として扱う。古い版へのダウングレードを修正版として案内しないため。

- Trivy JSON 入力の挙動は変えない。Trivy は修正版が無いときに `FixedVersion` を
  省略するという明確な意味を持つため、従来どおり「修正版なし」と表示する

#### エラー処理
- Phase 1 と同じく、利用者にスタックトレースを見せない。
  想定外の構造はすべて `InputError`（終了コード2）にする
- `vulnerabilities` / `affects` / `components` が配列でない等の型異常も
  分かりやすいメッセージで終了する。`components` は**入れ子の階層でも**同じ扱いにする
  （浅い階層だけ検証しても意味がないため）
- JSON の入れ子が深すぎて `RecursionError` になる入力も `InputError` にする
  （トレースバックを利用者に見せないため）

### 2. 英語レポート（`--lang en`）

#### CLI
- `--lang {ja,en}` を追加する。**既定は `ja`**（Phase 1 と同じ出力）
- 未対応の言語を指定した場合は argparse の使い方エラー（終了コード2）

#### 翻訳の対象
レポート本文に出る文字列すべて。具体的には:
- 見出し、対象名/生成日時/判定基準の行
- 外部データ取得失敗の警告文
- サマリ表（見出し・列名・各ランクの行動指針）
- 各ランクの節見出しと件数表記（「3件中 上位5件を表示」など）
- 一覧表の列名
- 優先度の理由文（「悪用確率は高い」等）
- 「不明」「あり」「なし」「修正版なし」等の値表記
- 末尾の「優先度の付け方」の説明と出典表記

#### 翻訳の対象外（今回やらない）
- **エラーメッセージ**（入力エラー等）は日本語のまま
- **`--help` の説明文**は日本語のまま
- 理由: 今回のスコープは「英語レポート対応」であり、CLI 全体の国際化ではない。
  中途半端に一部だけ英語化すると、かえって一貫性を欠く。
  必要なら Issue として起票し、別 Phase で扱う

#### 実装上の制約
- 訳文は **1箇所（`i18n` モジュール）に集約** する。
  各モジュールに日本語リテラルを散らさない
- パーサが値を読み取れなかったときに入れる表記（`(不明)` / `(名称不明)` /
  `(検出箇所不明)`）も翻訳の対象に含める。形式の解釈は言語に依存しないため、
  パーサは既定の表記を入れ、**表示するときにレポート言語へ差し替える**
- 日本語カタログと英語カタログは**同じキー集合を持つ**こと。
  これを検証するテストを置く（片方だけキーを足す事故を防ぐ）
- 日時の表記は両言語とも `YYYY-MM-DD HH:MM`（曖昧さが無く、ロケール依存を持ち込まないため）
- 優先度のランク名（`P0 (Act now)` 等）は両言語で共通。既に英語であり、
  ランクの識別子として翻訳しない方が分かりやすい

## 非機能要件
- **依存パッケージを増やさない**。i18n は標準の辞書で足りる範囲に留める
  （gettext / babel 等は導入しない）
- Python 3.11+ を維持。3.11 / 3.12 / 3.13 で CI が通ること
- pytest 全緑（Phase 1 の 145 件を含む）、ruff エラーなし
- 外部APIへの通信は Phase 1 から変えない。テストは引き続き外部に接続しない
- CycloneDX のサンプルは `tests/fixtures/` に置く。
  公開 CVE ID ＋架空のプロジェクト名のみで作る

## テスト要件
新規に以下を検証する。

**CycloneDX 正常系**
- サンプル SBOM から脆弱性が読み込める（件数・パッケージ名・バージョン・CVSS）
- 1つの脆弱性が複数 component に影響する場合、component ごとに行が分かれる
- `metadata.component` から対象名が取れる
- CVSS の選択規則（v3 優先 / nvd 優先 / v2 フォールバック）
- 修正版が `status: unaffected` から取れる

**CycloneDX 異常系**
- `vulnerabilities` が無い / 空 → 0件として正常終了
- `vulnerabilities` が配列でない → 入力エラー
- `affects` の参照先 component が存在しない → `(不明)` として残る
- ID 欠落・型異常のエントリは読み飛ばす
- CycloneDX でも Trivy でもない JSON → 入力エラー（終了コード2）

**形式の自動判別**
- CycloneDX ファイルを渡すと CycloneDX として読む
- Trivy ファイルを渡すと Trivy として読む（既存の挙動が変わらない）
- 両方の特徴を持つ入力でも判別結果が一意になる
- どちらでもない JSON は入力エラーになり、エラー文に両方の形式が書かれている

**英語レポート**
- `--lang en` でレポート全体が英語になる（日本語文字が残らない）
- 既定（`--lang` 省略）は日本語のまま
- 警告文・理由文・値表記が英語になる
- 不正な言語指定は終了コード2
- 日英カタログのキー集合が一致する
