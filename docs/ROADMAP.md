# ロードマップ

triage-lens の現状と、今後予定している改善をまとめます。

## v0.6.0 でできること

- Trivy の `--format json` 出力の読み込み
- CycloneDX（JSON）の SBOM の読み込み（形式は中身から自動判別。指定は不要）
- EPSS（悪用される確率）と CISA KEV（実際に悪用が確認されたカタログ）による優先順位付け（P0〜P3）
- 日本語・英語の Markdown トリアージレポート生成（`--lang en` で英語。既定は日本語）
- AI による対応方針コメント（`--ai`。APIキーを設定した場合のみ動作します）
- 深刻な検出があったときに CI を止めること（`--fail-on`）
- GitHub Actions への組み込み（`uses: secleeman/triage-lens@vX.Y.Z`）
- **本番依存と開発依存を分けた表示**（入力にその情報がある場合）
- **パッケージ単位の推奨アクション**（どれをどこまで上げれば何件片付くか）

### v0.6.0 で追加・変更したもの

実際のリポジトリ（npm / 263 パッケージ）で使ったときに、レポートを出したあとに
残っていた手作業を埋めました。**優先順位の付け方（P0〜P3）は変えていません。**

| 項目 | 内容 |
| --- | --- |
| 本番 / 開発の区別 | 入力にその情報があれば、レポートを「本番依存」「開発依存のみ」の2つの表に分けます。サマリにも「うち本番依存」の列が出ます。**区別できない入力では、区別せずに全件を表示し、その旨をレポートに明記します** |
| 推奨アクション | 「どのパッケージを、どの版まで上げれば、何件片付くか」をパッケージ単位の表にまとめます。**AI は使いません。`--top` の影響も受けません**（省略された検出も集約に含めます） |
| 判定の限界の明記 | レポートの最後に、依存関係にその版があるかどうかで判定していること、実際に使っているかまでは見ていないことを必ず書きます |
| Windows での入力の作り方 | Trivy の Windows バイナリが署名されておらず Smart App Control にブロックされる件と、その回避策（WSL / Docker / osv-scanner）を README に足しました |

**Trivy の JSON では本番 / 開発を区別しません。** Trivy の検出結果にその情報が
含まれていないためで、推測での分類はしません（Trivy は既定で開発依存を
スキャン対象から外します）。

### v0.5.0 で追加・変更したもの

CI に組み込めるようにしました。**優先順位の付け方とレポートの中身は変えていません。**

| 項目 | 内容 |
| --- | --- |
| CI を止める | `--fail-on p1` のように指定すると、そのランク以上の検出があったときに終了コードが 1 になります。**レポートは落ちるときも必ず生成されます** |
| GitHub Actions | ワークフローに数行書けば動きます。スキャン自体は行わず、スキャナが出力した JSON を渡して使います |
| 取得できなかったときの扱い | EPSS / CISA KEV を取得できないと判定は実際より甘くなります。**既定では警告を出すだけで終了コードは変えません**が、`--fail-on-fetch-error` を付けると終了コード 3 で止まります |

既定の挙動は変えていません。`--fail-on` を指定しなければ、これまでどおり
正常に処理できた限り終了コード 0 で終わります。

## 改善予定

### 入力形式を増やす

CycloneDX には対応しましたが、SPDX 形式はまだ読めません。
CycloneDX の XML 表現も未対応です（対応しているのは JSON のみ）。

`npm audit --json` と OSV 形式のネイティブ入力は、Phase 6 で実現性を調べました
（`docs/requirements-p6.md` の 6.）。要点は次のとおりです。

| 形式 | 見込み |
| --- | --- |
| `npm audit --json` | **CVE ID を持たない**（勧告は GHSA ID）ため、EPSS / KEV の引き当てができません。GHSA から CVE への変換に別のデータ源が要り、外部APIの方針（CLAUDE.md 4）に関わる判断が必要です |
| OSV JSON | `aliases` から CVE を取れる見込みがあり、追加のデータ源は不要です。ただし CVSS が数値ではなくベクタ文字列で入るため、その扱いを決める必要があります |

**当面は変換で回避できます。** osv-scanner は `--format cyclonedx-1-5` で脆弱性情報を
含む CycloneDX を出せるため、既存の CycloneDX 入力でそのまま読める見込みです。

### 外部API障害時の待ち時間を短くする

**現状の挙動**

外部API（EPSS / CISA KEV）が応答しない場合、最悪の待ち時間が入力のCVE件数に比例して伸びます。

- 1リクエストのタイムアウト: 20秒
- リトライ: 最大3回（待機 1秒 → 2秒）
- EPSS は 100件ごとにチャンク分割し、チャンクごとに上記が適用される
- KEV と EPSS は直列に実行される

例として、1,000件の異なるCVEを含む入力で接続がタイムアウトし続けた場合、
KEV 約63秒 + EPSS 10チャンク × 約63秒 = **10分以上** コマンドが返らない可能性があります。

処理そのものは止まらず、取得できなかったことをレポートに明記して結果を出しますが、
待ち時間が長いと「固まった」ように見えます。

**検討している改善案**

- enrichment 全体に実行時間の上限を設ける
- 同じホストへのリクエストが連続して失敗したら、残りのチャンクを試さず打ち切る（サーキットブレーカー）
- EPSS のチャンク問い合わせを並列化する
- 取得中であることを示す進捗表示を追加する

改善する際は、待機時間の合計を検証するテストも併せて追加する予定です
（現在の自動テストは待機処理を無効化しているため、この待ち時間はテストからは見えません）。

### そのほか把握している課題

| 課題 | 現状 |
| --- | --- |
| CycloneDX の `specVersion` を検証していない | 脆弱性情報を表現できない 1.3 以前の SBOM も「検出0件」として受理します。エラーにするか注記を出すか検討中です |
| エラーメッセージと `--help` が日本語のまま | `--lang en` で英語になるのはレポート本文だけです |
| 重複した検出で修正バージョンが比較できない場合 | Debian の `1:1.2.11.dfsg-2+deb11u2` のような表記は比較せず「不明」と表示します（誤った修正版へ誘導しないための安全側の挙動です） |

## 対応予定のないもの

- AI にパッチや修正 PR を作らせること（`--ai` が書くのは対応方針の文章だけです）
- AI に優先順位そのものを判定させること
- **到達性の解析**（脆弱なコードが実際に呼ばれるかの判定）。レポートには判定の限界として明記しますが、解析そのものは行いません
- Web UI
