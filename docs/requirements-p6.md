## 背景 — 実戦で見つかった「手作業の隙間」

実在の Web サイトのリポジトリ（npm / 263 パッケージ）に triage-lens をかけたところ、
レポートは出たものの、**その後に人手の作業が残った**。残った作業は3つ。

| # | 残った手作業 | 何が足りなかったか |
| --- | --- | --- |
| 1 | 検出を本番依存と開発依存に人が仕分けた | ビルドツールやテスト用の依存も同じ表に並ぶ。「P2 17件」のうち利用者に影響しうるのが何件なのかが読めない |
| 2 | 同じパッケージの検出を人がまとめた | 1つのパッケージが複数のCVEで何行にも出る。実際の作業は「そのパッケージを1回上げる」だけ |
| 3 | 「依存にある＝危ない」と読まれた | 該当機能を使っていなければ実害が無いことがある。レポートにその但し書きが無い |

Phase 6 はこの3つを埋める。

## ゴール

レポートを見た人が、**そのまま作業に移れる**ようにする。

- どれが本番に効く問題で、どれが開発中だけの問題かが、表の見た目で分かる
- 「どのパッケージをどの版に上げれば、いくつ片付くか」が1つの表にまとまっている
- このレポートで分かることの限界が、レポート自身に書いてある

## 機能要件

### 1. 本番依存 / 開発依存の区別

#### 1-1. 事前調査の結果（この設計の前提）

実装方針を決める前に、生成ツールが実際に何を出しているかを調べた。結果は次のとおり。

| 調べたこと | 分かったこと | 出典 |
| --- | --- | --- |
| CycloneDX の `scope` の値 | `required` / `optional` / `excluded` の3値。**省略時は `required` とみなす**のが仕様 | CycloneDX 仕様 |
| `excluded` の意味 | テストや開発など**実行時に到達しない**部品 | 同上 |
| `optional` の意味 | 実行時に**任意**（＝使われうる）。「開発用」という意味ではない | 同上 |
| Trivy の CycloneDX 出力 | **`scope` を書かない。** そもそも開発依存を既定でスキャン対象から外している | Trivy メンテナ回答（aquasecurity/trivy Discussion #9786） |
| npm 本体の `npm sbom --sbom-format cyclonedx` | dev を `scope` では表さない。`scope` に入るのは `optional` / `required` のみ。dev は **`properties[]` の `cdx:npm:package:development` = `"true"`** で表す | npm CLI の実装（`lib/utils/sbom-cyclonedx.js`） |
| CycloneDX 公式の cyclonedx-npm | devDependencies に `scope` を付けていない（要望 issue が open のまま） | CycloneDX/cyclonedx-node-npm #1151 |

**この調査から出る結論は2つ。**

1. **`scope` だけを見る実装は成立しない。** npm の現場でいちばん出回る `npm sbom` の
   出力は、dev を property でしか表さない。`scope` と `properties` の両方を見る。
2. **`optional` を開発依存に含めてはいけない。** npm は `optionalDependencies` と
   `devOptional` に `optional` を付ける。これらは実行時に使われうるもので、開発専用ではない。
   オーナー指示の文面は「本番(required)と開発(optional/excluded)」だったが、調査の結果
   この対応付けは誤りだと判断した（→ 裁定 1）。

#### 1-2. 判定の手順（component 1件ごと）

上から順に見て、最初に当てはまったところで決める。

1. `properties[]` に既知の「開発依存」を示す項目があれば → **開発依存のみ**
   - 当面の対象: `cdx:npm:package:development` の値が `"true"`
   - 対象は表として1箇所にまとめ、あとから足せるようにする。**特定のCVEや日付に依存する
     分岐は作らない**（CLAUDE.md 7）。これは生成ツールごとの項目名の対応表であって、
     個別事例への分岐ではない
2. `scope` が `excluded` → **開発依存のみ**
3. `scope` が `required` / `optional` / 省略 → **本番依存**
4. 脆弱性の `affects[].ref` に対応する component が SBOM に無い → **本番依存**

**迷ったら本番依存に倒す。** 本番のものを「開発だけ」の側に入れると見落としになる。
逆は「多めに出る」だけで見落としにはならない。安全側は本番側。

#### 1-3. 入力全体を「区別できる / できない」で分ける

`scope` は省略時に `required` とみなす仕様なので、**何も書かれていない SBOM をそのまま
読むと「全件が本番依存」に見えてしまう**。これは区別できているのではなく、区別する材料が
無いだけ。両者を混同しない。

| 状態 | 条件 | レポートの見せ方 |
| --- | --- | --- |
| 区別できる | `components[]` の**1件以上**に明示的な信号がある（`scope` キーが実際に書かれている、または既知の property がある） | 本番依存 / 開発依存のみ に分けて表示 |
| 区別できない | 明示的な信号が1つも無い | 従来どおり1つの表。冒頭に「区別情報なし」の1行を出す |

判別の材料は `components[]` 配下だけを見る。**`metadata.component`（スキャン対象
そのもの）は見ない。** あれは依存ではなく、そこに `scope: required` と書かれていても
依存の区別については何も分からない。含めると、材料が無いのに「区別できた（全件が
本番依存）」というレポートを出してしまう。

「区別できない」ときに出す文言（案）:

- ja: `この入力には本番依存 / 開発依存を区別する情報が含まれていないため、区別せずに全件を表示しています。`
- en: `This input carries no information distinguishing runtime from development dependencies, so all findings are listed together.`

置き場所は、既存の取得失敗警告（`> ⚠️ ...`）と同じ位置。警告ではないので `⚠️` は付けない。

#### 1-4. 各ランクの節の見せ方（区別できる場合）

`## P2 (Medium) — 計画的に対応（17件）` の下を、2つの表に分ける。

```
### 本番依存（3件）
| CVE | パッケージ | ... |

### 開発依存のみ（14件）
| CVE | パッケージ | ... |
```

- 片方が0件のときも、見出しと「該当なし。」の1行を出す（**表ごと消さない**。
  「本番依存 0件」であることが、いちばん伝えたい情報になる場面があるため）
- 並び順は既存の `sort_key` のまま。本番 / 開発でグループ化するだけ
- `--top` は**表ごとに**適用する（→ 裁定 6）

#### 1-4-1. 開発依存が0件のとき（2026-08-30 追加裁定）

**レポート全体で開発依存の検出が1件も無い場合は、分割そのものをやめて従来形式にする。**
空の「開発依存のみ（0件）」がランクの数だけ並ぶだけで、読む人には何も足さないため。
サマリの内訳の列も出さない（件数と同じ数が並ぶだけになる）。

ただし、**「材料が無くて分けられなかった」のと「区別したうえで0件だった」のは
書き分ける。** 読む人にとって意味がまったく違う。サマリに1行入れて見分けられるようにする。

| 状態 | 表示 | 出す文言 |
| --- | --- | --- |
| 区別できない | 1つの表・3列 | 冒頭に `> この入力には本番依存 / 開発依存を区別する情報が含まれていないため、…` |
| 区別できて開発依存が0件 | 1つの表・3列 | サマリに `開発依存のみの検出: 0件（すべて本番依存です）` |
| 区別できて開発依存がある | 2つの表・4列 | （どちらの文言も出さない） |

**本番依存が0件のときは分割を続ける。** 「本番依存 0件」はいちばん伝えたい情報であり、
1-4 の判断をそのまま適用する。非対称なのは意図したもの。

#### 1-5. サマリ表

区別できるときだけ、内訳の列を1つ足す。

```
| 優先度 | 件数 | うち本番依存 | 目安 |
| --- | --- | --- | --- |
| P0 (Act now) | 2 | 2 | 今すぐ対応 |
| P2 (Medium) | 17 | 3 | 計画的に対応 |
```

区別できないときは従来の3列のままにする。区別できないのに空欄や `-` の列を出すと
「本番依存は0件」と読まれる（→ 裁定 2）。

#### 1-6. Trivy JSON 入力 — **対応しない**（調査結果）

調べた結果、**Trivy の JSON からは本番 / 開発を取れない**。よって従来表示のままとし、
推測での分類はしない（CLAUDE.md 7）。

| 調べたこと | 結果 |
| --- | --- |
| `Results[].Vulnerabilities[]` に dev/prod の項目はあるか | **無い。** `DetectedVulnerability` の項目は VulnerabilityID / VendorIDs / PkgID / PkgName / PkgPath / PkgIdentifier / InstalledVersion / FixedVersion / Status / Layer / SeveritySource / PrimaryURL / DataSource / Fingerprint / Custom と脆弱性本体のみ |
| `Dev` はどこにあるか | `Results[].Packages[]`（パッケージ一覧）側。ここは **`--list-all-pkgs` を付けたときだけ出る** |
| `PkgID` で突き合わせられないか | 理屈上は可能。ただし後述の理由で採らない |
| Trivy の既定の挙動 | **既定で開発依存をスキャン結果に出さない**（`--include-dev-deps` を付けたときだけ出る） |

`PkgID` での突き合わせを採らない理由:

1. 利用者に `--list-all-pkgs` を強制することになる。付け忘れた入力では黙って区別が消える
   （「静かに壊れた」状態を作らない、という既存の方針に反する）
2. `PkgID` は省略されうる項目で、突き合わせに失敗した検出の扱いが増える
3. そもそも Trivy は既定で開発依存を出さない。区別が要るのは `--include-dev-deps` を
   付けた入力に限られ、費用対効果が合わない

**Trivy JSON でも 1-3 の「区別情報なし」の1行は出す。** なぜ分かれていないのかを利用者に
示すため（黙って従来表示に戻すと、機能が壊れているように見える）。

再検討する条件: Trivy が `Vulnerabilities[]` 側に dev を出すようになったとき。

### 2. パッケージ単位の推奨アクション

レポートに `## 推奨アクション` の節を1つ足す。**ルールベースのみ**で作る。
`--ai` を付けなくても出るし、付けても内容は変わらない。

#### 2-1. 集約の単位

**`(パッケージ名, 現在バージョン)`** でまとめる。検出箇所（Target）は跨いでまとめる。

- 実際の作業は「このパッケージをこの版に上げる」であり、同じ版が2箇所にあっても作業は1つ
- 版が違えば別の行にする（上げ先が変わるため）

例: `urllib3 1.26.4` が `app/requirements.txt` と `worker/requirements.txt` の
2箇所で見つかった場合 → 推奨アクションは1行。

#### 2-2. 表の形

```
| パッケージ | 現在 | 上げ先 | 解消されるCVE | 最高優先度 |
| --- | --- | --- | --- | --- |
| lodash | 4.17.15 | 4.17.21 | 3件 | P1 (High) |
| urllib3 | 1.26.4 | 1.26.18 | 2件（ほかに1件は修正版なし） | P2 (Medium) |
| apt | 2.2.4 | 修正版なし | 0件 | P3 (Low) |
```

列は5つに固定する。検出箇所は列にしない（→ 裁定 4）。

#### 2-3. 「上げ先」の決め方

そのパッケージの検出のうち、**修正版が判明しているものだけ**を集めて決める。

1. 集めた修正版が0件 → 全部が「修正版なし」なら **`修正版なし`**、「不明」が混じるなら
   **`不明`**（既存の「修正版なし」と「不明」の区別を保つ）
2. 全部が同じ文字列 → その値
3. 全部が**確実に比較できる形式**（`1.2.3` のような数字とドットだけ）→ **最大値**
4. 比較できない形式が混ざる → **`不明`**

4 の理由は既存の重複マージと同じ。`1:1.2.11.dfsg-2+deb11u2` のような表記を独自に解釈すると、
**古い版へのダウングレードを「上げ先」として案内しかねない**。既存の
`parsing._newer_version` / `_version_parts` をそのまま再利用する（判定規則を2箇所に分けない）。

#### 2-4. 「解消されるCVE」の数え方

- **上げ先へ更新することで解消される件数** = そのパッケージの検出のうち、修正版が判明
  しているCVEの数（同じCVE IDは1件と数える）
- 修正版が「なし」「不明」のCVEがある場合は、同じセルに件数を併記する
  （例: `2件（ほかに1件は修正版なし）`）。**別の列は作らない**
- 上げ先が `修正版なし` / `不明` の行は `0件`

#### 2-5. 修正版が全て不明 / 無いパッケージの扱い

**表から落とさない。** 上げ先を `修正版なし` または `不明`、解消件数を `0件` として、
並びの最後に置く。落とすと「表に載っていない＝対応不要」と読まれる。実際には「このツール
では上げ先が決められない、人が調べる必要がある」という意味になる。

#### 2-6. 並び順

1. 最高優先度の高い順（P0 → P3）
2. 解消されるCVE件数の多い順
3. パッケージ名の辞書順

上げ先が `修正版なし` / `不明` の行は、上の順序に関わらず**最後にまとめる**。

#### 2-7. 対象範囲と `--top` の関係

- **`--top` の影響を受けない。** 省略された P2 / P3 の検出も集約に含める
- 理由: 表に出ていない検出が、表に出ているパッケージと同じことがある。`--top` で切った分を
  落とすと、解消件数が実際より少なく出て「上げても片付かない」ように見える
- この点はレポート本文にも1行書く
  （例: `この表は表示件数の指定（--top）に関わらず、検出されたすべてを対象にしています。`）
- 行数の上限は設けない。パッケージ単位に畳むので、行数は必ず検出件数以下になる

#### 2-8. 区別できる入力での分け方

1-4 と同じく「本番依存」「開発依存のみ」の2つの表に分ける。列は増やさない。
1つのパッケージが本番と開発の両方に現れた場合は**本番依存の表にだけ**出す
（作業は1回で済むため。開発側にも同じ行を出すと二重に見える）。

### 3. 実害判定の限界の注意書き

レポートの**最終行**に、固定の注意書きを1〜2行置く。入力や結果によって文面は変えない。

文案:

- ja:
  `この判定は「その版が依存関係に含まれているか」に基づいています。該当する機能を実際に使っているか、外部から到達しうるかまでは見ていないため、実際の影響はここに書かれたものより小さいことも大きいこともあります。`
- en:
  `These priorities are based on whether an affected version is present in your dependencies. Whether the affected code is actually used, or reachable from outside, is not assessed - the real impact may be smaller or larger than shown here.`

- 検出が1件以上あるときに出す。検出0件のときは出さない（→ 裁定 8）
- 見出しは付けず、本文1段落として置く

### 4. レポートの節の並び（決め）

```
1. タイトル / メタ情報
2. 警告（外部データの取得失敗）／ 区別情報なしの注記    ← 1-3 で追加
3. サマリ                                            ← 1-5 で列が増えることがある
4. P0 / P1 / P2 / P3 の各節                          ← 1-4 で2つの表に分かれることがある
5. 推奨アクション                                     ← 新規（2.）
6. 優先度の付け方
7. 対応方針コメントについて（--ai を使ったときだけ）
8. 実害判定の限界の注意書き                            ← 新規（3.）
```

「推奨アクション」を「優先度の付け方」より前に置く理由: 「優先度の付け方」は判定基準の説明
であって読み物の付録にあたる。行動の指示をその後ろに置くと埋もれる（→ 裁定 3）。

見出しの記法は既存に合わせて `## 推奨アクション` とする。オーナー指示の文面にあった `■` は
使わない（→ 裁定 7）。

### 5. README（日英）— Windows での入力ファイルの作り方

`## 使い方 > 1. スキャンして JSON を出す` の直後に、新しい小節を足す。

#### 5-1. 書くこと

1. **事実**: Trivy が配布する Windows 向けバイナリには署名が無いため、Smart App Control や
   SmartScreen が有効な環境では実行がブロックされることがある。triage-lens 側では回避できない
2. **代わりに使える経路**（いずれも triage-lens が読める形式を出せる）
   - WSL 上の Trivy — `trivy fs . --format json -o result.json`。出力先を Windows 側から
     読めるパスにする
   - Docker Desktop 経由の Trivy — リポジトリをマウントして `trivy fs` を実行する
   - osv-scanner の CycloneDX 出力 — `--format cyclonedx-1-5`。**脆弱性情報を含む**ので
     triage-lens に渡せる（→ 実装時に実データで要検証）
3. **よくある誤解を1つ潰す**: `npm sbom --sbom-format cyclonedx` の出力には
   `vulnerabilities` が無い。**部品表であって脆弱性リストではない。** そのまま渡すと
   triage-lens は「検出0件」と出す（これは仕様どおりの動作で、安全という意味ではない）
4. `npm audit --json` は現時点では読めない（→ 6.）

#### 5-2. 書かないこと

- Smart App Control の無効化手順、SmartScreen の除外設定、`Unblock-File` などの回避手順。
  **セキュリティ設定を下げる案内はしない。**「別の経路を使う」だけを示す
- 特定のバージョン番号やダウンロード URL の直書き（陳腐化するため）

#### 5-3. 英語版

`README.en.md` に同じ節を対応する位置に足す。内容は同じにする（日英で情報量を変えない）。

### 6. 調査項目 — npm audit / OSV のネイティブ入力（**今回はスコープ外**）

Phase 7 以降の判断材料として、実現性とコストだけを記載する。**Phase 6 では実装しない。**

#### 6-1. npm audit JSON（`auditReportVersion: 2`）

| 項目 | 内容 |
| --- | --- |
| 構造 | `vulnerabilities` をパッケージ名でキーにした辞書。各エントリに `severity` / `isDirect` / `fixAvailable` / `via[]` |
| **最大の障害** | **CVE ID が無い。** 勧告は GHSA ID（`https://github.com/advisories/GHSA-...`）で表される |
| なぜ問題か | triage-lens の EPSS / CISA KEV の引き当ては **CVE ID が前提**。GHSA のままでは優先順位が付けられない |
| 解決に要るもの | GHSA → CVE の変換。OSV.dev API など**別のデータ源の追加**が必要 |
| 規範との関係 | **CLAUDE.md 4（外部APIは NVD / EPSS / CISA KEV のみ）に抵触する。** データ源を増やすかどうかはオーナーの判断が要る |
| 修正版の情報 | `fixAvailable` は真偽値または `{name, version, isSemVerMajor}`。「どの版に上げれば直るか」を常に与えるわけではない |
| CVSS | GitHub Advisory 由来の値のみ。NVD の値は入らない |
| 見積り | **中〜大。** 新しい入力モジュール + GHSA 解決の仕組み + テスト。データ源追加の判断が前提条件 |

#### 6-2. OSV JSON（`osv-scanner --format json`）

| 項目 | 内容 |
| --- | --- |
| 構造 | `results[].packages[].vulnerabilities[]` と `groups[]` |
| CVE の取得 | `aliases` に CVE が入ることが多く、**追加の API 呼び出しなしで CVE を得られる**見込み |
| 修正版 | `affected[].ranges[].events[].fixed`。エコシステムごとに複数のレンジがあり、「どれが手元の版に対する修正か」の解釈が要る。CycloneDX の `unaffected` より難しい |
| CVSS | `severity[]` に CVSS ベクタ文字列。**数値スコアが直接は入らない**ことがある。ベクタから数値を計算する仕組みを自前で持つかどうかの判断が要る |
| 見積り | **中。** CVE は取れるが、CVSS の扱いが論点として残る |

#### 6-3. 当面の回避策（Phase 6 の README に書くこと）

osv-scanner は `--format cyclonedx-1-5` で**脆弱性情報を含む CycloneDX** を出せる。
ネイティブ対応をしなくても、**既存の CycloneDX 入力でそのまま読める見込み**
（実装時に実データで要検証）。

#### 6-4. 判断の材料

- ネイティブ対応の価値は「利用者が変換の一手間を省ける」ことに尽きる。CycloneDX 経由で
  読めるなら、値は小さい
- npm audit 対応は、規範（CLAUDE.md 4）に触れるデータ源の追加とセットになる
- **推奨: Phase 6 では対応しない。** まず osv-scanner の CycloneDX 出力が実際に読めるかを
  確かめ、読めるならネイティブ対応は見送る

## 裁定（2026-08-30 オーナー裁定・確定）

論点10件はすべて推奨案どおりで承認された。以下は**決定事項**であり、実装はこれに従う。

| # | 論点 | 決定 | 理由 |
| --- | --- | --- | --- |
| 1 | `scope: optional` の扱い | **本番依存として扱う** | npm は実行時に使われうる依存に `optional` を付ける。開発扱いにすると本番の問題が「開発だけ」の表に隠れる |
| 2 | サマリの列数 | **区別できるときだけ4列。できないときは従来の3列** | 区別できないのに列があると「本番0件」と誤読される |
| 3 | 推奨アクションの位置 | **各ランクの直後（「優先度の付け方」の前）** | 行動の指示が判定基準の説明の後ろに埋もれない |
| 4 | 「検出箇所の数」列 | **足さない（5列固定）** | 作業単位は「1回上げる」で、箇所数は作業量を変えない。表が横に伸びる代償が大きい |
| 5 | 開発依存と `--fail-on` | **対象から外さない（現状維持）** | Phase 6 は表示の変更に留める。CI を通す条件を変えるのは別の意思決定 |
| 6 | 区別できるときの `--top` | **表ごとに N 件（本番 N + 開発 N）** | ランク全体で N 件にすると、本番の検出が開発依存に押し出されて見えなくなる |
| 7 | 推奨アクションの見出し記法 | **`## 推奨アクション`（`■` は使わない）** | 既存の見出しはすべて `##`。記法が混ざると目次や機械処理が崩れる |
| 8 | 限界の注意書きの出し分け | **検出が1件以上のときだけ出す** | 判定対象が無いときに判定の限界を書いても意味が伝わらない |
| 9 | `examples/` の npm 系サンプル | **足す** | 区別が付いたレポートがどう見えるかは、文章より現物のほうが早い |
| 10 | 版数とリリース | **v0.6.0 で一括** | 3つの変更はどれもレポートの見た目に関わる。分けて出すと examples の作り直しが2回になる |

あわせて、次の方針も支持を得た。

- Trivy JSON を非対応とする結論（1-6）
- `npm sbom` の出力に脆弱性情報が無いことを README に明記する方針（5-1）
- Smart App Control / SmartScreen の回避手順を書かない方針（5-2）

### スコアリング不変の担保（追加指示）

「スコアリングを変更しない」ことを**テストでも担保する**。方針は `tests/test_scoring_unchanged.py`
（新規）で、次の3つを固定する。

1. `EPSS_THRESHOLD` / `CVSS_THRESHOLD` の値
2. `classify()` の決定表（KEV の有無 × EPSS の高低・不明 × CVSS の高低・不明 の全組み合わせ）
3. 本番 / 開発の区別が優先度と理由文に**影響しないこと**（同じ入力で `dev_only` だけを
   変えても結果が一致すること）

このファイルは Phase 6 の変更で1件も落ちてはならない。落ちたら設計が間違っている。
